# Why the Tauri Android network slice needs recoverable routing

## The question and code anchor

Why is issue [#9](https://github.com/raymondctc/mobile-capture/issues/9) a separate network-capture extension to the log-only Tauri PoC, and which lifecycle constraints should shape it? The current Tauri owner, lease, and worker are in `TauriPoC/capture-core/src/{owner,process,worker}.rs` and `TauriPoC/src-tauri/src/lib.rs`. The existing Android routing model is in `Sources/Core/CaptureLifecycle/{AndroidCaptureRouting,NativeCaptureHost,NativeCaptureRouting,CaptureLifecycleFiles}.swift`.

Issue and PR text posted under the repository owner account was produced during this agent-assisted task. It records the working contract. It is not independent evidence of a human architectural decision.

## What the records say directly

- **[Recorded issue contract]** Issue #7 was opened [issue #7](https://github.com/raymondctc/mobile-capture/issues/7) to test a portable Tauri 2/Rust Android path because the AppKit/SwiftUI, Darwin process, and macOS packaging stack excludes Windows users. The first PoC deliberately deferred mitmproxy and device routing until restoration and failure recovery could be verified. Its acceptance criteria require fake-tool failure checks before real routing.
- **[Recorded design contract]** The [issue #7 owner comment](https://github.com/raymondctc/mobile-capture/issues/7#issuecomment-6296215992) selected one Rust capture owner behind Tauri commands and a small leased collector. Whole-device logs came first; app scope and live network capture were visibly unavailable because a partial port of identity filtering or proxy recovery would weaken the existing guarantees.
- **[Direct, author description]** [PR #8](https://github.com/raymondctc/mobile-capture/pull/8) calls the log-only PoC a portability test before full migration. It records partial forced-stop cases and distinguishes Windows build/fixture evidence from phone-hardware acceptance. At investigation time it was open and unmerged; [issue #9](https://github.com/raymondctc/mobile-capture/issues/9) explicitly builds on it.
- **[Recorded issue contract]** [Issue #9](https://github.com/raymondctc/mobile-capture/issues/9) says the log-only PoC cannot capture HTTP(S), which requires portable process ownership and recoverable device routing. It asks for whole-device mitmproxy capture, raw flows, HAR, bodies, canonical timeline events, truthful partial outcomes, network UI, and actual traffic export.
- **[Recorded issue contract]** [Issue #9](https://github.com/raymondctc/mobile-capture/issues/9) requires a loopback proxy and session-owned ADB reverse endpoint; exact routing intent persisted before mutation; verified settings restoration while the proxy is alive; preservation of external changes; recovery state after disconnect or failure; and contracts before implementation. It calls for fake-tool rollback/conflict/parent-loss probes, controlled loopback HTTP(S), clearly labeled fixtures, and macOS/Windows CI. It forbids live phone routing or certificate changes during fixture verification.
- **[Direct, scope]** [Issue #9](https://github.com/raymondctc/mobile-capture/issues/9) excludes app scope, iPhone, shared host proxy changes, automatic CA trust, and production distribution. It also keeps the shipping Swift app, release configuration, and log-only PoC intact. Manual CA trust is stated in [the local plan](/Users/raymond/workspace/mobile-capture/.audit/tauri-network-plan.md) (Outcome).
- **[Direct, physical finding]** `docs/CAPTURE-PROOF.md:62-93` records a Pixel 4a/Android 13 case where restoring stored settings left Android's ConnectivityService/NetworkMonitor probing a closed capture port. A `:0` clear and normalized acknowledgment restored Wi-Fi validation; a later Start/Stop checked originally unset values and zero reverse tunnels. `CaptureRuntime/capture_runtime.py:259-298` explains the legacy proxy-handler and repeated-write notification behavior.

## What implementation and tests establish

- **[Observed implementation]** `AndroidCaptureRouting.swift:31-101,123-165` snapshots presence and exact values for five global proxy fields, refuses an occupied `adb reverse` endpoint with `--no-rebind`, journals intent before changes, verifies the applied snapshot, refuses externally changed values, performs the `:0` clear with an empty-value retry, restores exact originals, and removes only its own reverse mapping after proxy restoration. `CaptureLifecycleFiles.swift:33-85` provides synchronized private journal writes and a shared per-user lock.
- **[Observed implementation]** `NativeCaptureHost.swift:100-149,218-255,279-329` prepares a loopback listener before routing, restores routing before closing workers, retains a living supervisor/proxy and lock on restoration failure, and retries orphan restoration under the same lease. `NativeCaptureRouting.swift:64-68` uses the journaled ADB path and device for recovery. `Tests/NativeCaptureLifecycleTests.swift:334-375,413-455,536-559,621-667` exercise retry, conflict, proxy-alive restoration, and orphan evidence behavior in synthetic tests.
- **[Observed implementation]** The current PoC holds `CaptureOwner` in GUI Tauri state; window close/exit invokes Stop without handling its error (`src-tauri/src/lib.rs:11-21,92-107`). `Lease::close` drops the worker pipe, EOF requests collector stop, and Windows Job containment is held inside the GUI-owned lease (`owner.rs:55-73`, `worker.rs:40-49`, `process.rs:105-149`). The PoC's unverified-shutdown/export guard covers its collector, not Android routing (`owner.rs:177-201,321-350`).

## What we can reasonably infer

- **[Inferred]** The network owner appears to need a lifetime independent of GUI close: issue #9 requires parent-closure recovery and proxy continuity through restoration, while the current GUI lease/Windows Job closes or kills its workers on GUI exit. A separate guardian with its own routing lease, proxy ownership, durable journal, and private retry control is one viable shape, but the issue does not select an executable or IPC protocol. [Issue #9](https://github.com/raymondctc/mobile-capture/issues/9); `owner.rs:55-73`; `process.rs:105-149`; `NativeCaptureHost.swift:218-235`.
- **[Inferred]** An isolated Tauri output directory alone appears insufficient for safe routing: the Swift app uses a per-user lock across output roots, while the PoC owner has no routing lock. A macOS network owner likely needs to coordinate with that lock; a Windows equivalent remains to be designed. `CaptureLifecycleFiles.swift:50-85`; `TauriPoC/capture-core/src/owner.rs:91-175`.
- **[Inferred]** Database equality alone seems insufficient as the Android restoration success condition, given the physical stale-runtime finding and the Swift clear/acknowledgment flow. `docs/CAPTURE-PROOF.md:62-93`; `AndroidCaptureRouting.swift:80-101,133-156`.

## Preserve, change, avoid, risk

- **Preserve:** Exact five-field presence/value snapshots; no-rebind endpoint ownership; write-ahead mutation journal; full-snapshot checks; conflict preservation; clear/acknowledge/retry; exact restore before reverse removal; private synchronized recovery state; cross-session exclusion. These are existing Swift behaviors (`AndroidCaptureRouting.swift:31-101,123-165`; `CaptureLifecycleFiles.swift:33-85`) and align with [issue #9](https://github.com/raymondctc/mobile-capture/issues/9).
- **Change:** The network controller needs to own the proxy, routing lease, and retry state beyond GUI closure. The GUI can request Stop and present recovery, but cannot be the sole keeper of a live proxy. This is a design inference from the existing GUI-owned lease and [issue #9](https://github.com/raymondctc/mobile-capture/issues/9), not a recorded choice of guardian binary.
- **Avoid:** Treating `Lease::close` as network Stop, trusting disk PIDs as live process authority, removing an external reverse mapping, finalizing a terminal package while restoration is unknown, or claiming Android runtime recovery from stored settings alone. Existing paths show why (`owner.rs:55-65`; `NativeCaptureHost.swift:121-149,218-255`; `AndroidCaptureRouting.swift:93-101`; `docs/CAPTURE-PROOF.md:62-93`).
- **Risk:** A living native supervisor keeps the proxy up after restore failure, but its hard death closes worker keepalive pipes and can stop the listener before later journal recovery (`CaptureHostProcesses.swift:39-56`; `NativeCaptureHost.swift:121-149`). The crash test establishes partial evidence/retry, not uninterrupted proxy service (`NativeCaptureLifecycleTests.swift:621-667`). This distinction must constrain any Tauri availability claim.
