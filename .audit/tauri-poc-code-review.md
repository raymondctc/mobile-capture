# Final bounded-group correctness review

Reviewed exact delivery HEAD `1f00f56298c3d2379e3db73202cc433801aad70a` against `6231276` and the accepted logs-only PoC contract. Status: **CLEAN**. I found no actionable correctness issue in the bounded shutdown correction.

The Unix worker checks the leader with `waitid(... WNOWAIT)` and keeps it unreaped through both group signals. After SIGTERM, it requires the leader to exit, stdout's reader to close, and stderr's reader to finish within one second. It escalates to group SIGKILL if any condition remains incomplete, then gives the same conditions one more second. It writes a receipt only after the readers finish and the leader is reaped. This closes the earlier case where a SIGTERM-resistant descendant held an inherited pipe open after its leader exited. The stderr reader now stores at most 8 KiB but continues reading to EOF, so the diagnostic cap cannot itself stall shutdown.

I extracted exact HEAD to `/private/tmp/mobile-capture-bounded-independent` and ran `cargo test --test unix_group -- --nocapture` there. All four focused tests passed, covering 12 leader and descendant combinations: clean exit, exit 23, and SIGUSR1, each with responsive or SIGTERM-resistant descendants and the stderr-only variants. The tests assert descendant death, worker completion, the retained raw row, receipt reason and exit code, `child_reaped`, `forced`, and stderr contents. The initial run inside the default sandbox could not bind the fixture Unix socket (`EPERM`); the same tests passed outside that sandbox. No delivery files or worktrees were changed.

The Windows branch still uses the child process handle through `try_wait` and termination, with its prior forced-partial semantics. The shared drain loop has no Unix-only call outside `cfg(unix)`. The accepted limits remain: a worker killed abruptly on macOS may leave its client, and a second incomplete deadline returns an error with no verified receipt. The latter is preferable to claiming shutdown was verified.
